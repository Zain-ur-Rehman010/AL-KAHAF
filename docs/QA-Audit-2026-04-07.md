### 1.2 Bug Report — HIGH PRIORITY

#### BUG-01 · `localStorage` Key Inconsistency (Auth Token)
**Severity:** Critical  
**Affected Pages:** ~12 admin/instructor pages  
**Description:** `authController.js` saves the token as `accessToken`. However, several pages read it using the wrong key names (`token`, `adminToken`, `authToken`), causing silent auth failures — the page loads but all API calls return 401.

| Page | Key Used | Status |
|---|---|---|
| `admin-profile.html` | `token` | Wrong |
| `blog-list.html` | `adminToken` | Wrong |
| `welfare-program-add.html` | `accessToken` (with fallbacks) | Fixed |
| `admin-dashboard.html` | `accessToken` (with fallbacks) | Fixed |
| Most welfare pages | `accessToken` (with fallbacks) | Fixed |

**Fix:** Standardize all pages to `localStorage.getItem('accessToken')`.

---

#### BUG-02 · Hardcoded API Base URL (15+ Pages)
**Severity:** High  
**Affected Pages:** `free-trial.html`, `course-grid.html`, `blog-grid.html`, some admin pages  
**Description:** Several pages hardcode `http://localhost:5000/api/v1` instead of using the centralized `API_CONFIG.BASE_URL` from `api-config.js`. This means the live site sends API calls to localhost, which always fails in production.

**Fix:** Load `api-config.js` in every page and replace all hardcoded base URLs with `API_CONFIG.BASE_URL`.

---

#### BUG-03 · `become-an-instructor.html` Form Not Wired
**Severity:** High  
**Description:** The "Become an Instructor" page has a fully designed form but there is no backend route (`POST /api/v1/instructor-applications` or similar) and no JavaScript to submit it. Submitting the form does nothing.

**Fix:** Create a backend route + controller to handle applications, and wire the frontend form to it.

---

#### BUG-04 · `impact`, `fundUse`, `milestones` Not Saved in Welfare Programs
**Severity:** High (just fixed in this session)  
**Description:** The `WelfareProgram` model was missing the `impact`, `fundUse`, and `milestones` columns. Admin form collected and sent these fields but they were silently dropped by the backend.

**Fix:** Added JSON columns to model + controller (done in this session). Restart backend to `sync({alter:true})`.

---

#### BUG-05 · `console.log` Statements Left in Production Code
**Severity:** Medium  
**Affected Pages:** 16 frontend pages including `admin-dashboard.html`, `admin-settings.html`, `courses-list.html`, `enrollments-list.html`, `students-list.html`, `course-grid.html`, `instructor-course.html`, etc.  
**Description:** Debug `console.log` calls expose internal data structures (API responses, user objects, token values) in the browser console on the live site. This is a security concern.

**Fix:** Grep and remove all `console.log` before deploying to production.

---

#### BUG-06 · Enrollment Confirmation Email Never Sent
**Severity:** Medium  
**Description:** `emailService.sendEnrollmentConfirmation()` is fully implemented but is never called in `enrollmentController.js`. Students receive no email after enrolling in a course.

**Fix:** Call `sendEnrollmentConfirmation(user, course)` inside the `enrollCourse` controller after successful payment/enrollment. Wrap in a non-blocking try/catch.

---

#### BUG-07 · Certificate Email Never Sent
**Severity:** Medium  
**Description:** `emailService.sendCertificateEmail()` is implemented but never called in `enrollmentController.issueCertificate`. Students do not receive their certificate email.

**Fix:** Call `sendCertificateEmail(user, course, certificate)` after certificate is issued. Non-blocking.

---

#### BUG-08 · Welcome Email Not Awaited
**Severity:** Low  
**Description:** `sendWelcomeEmail()` is called in `authController.js` during OTP verification but is not `await`-ed and not wrapped in try/catch. If the email fails, an unhandled promise rejection can occur.

**Fix:** Wrap in try/catch or use `.catch(() => {})` pattern.

---

#### BUG-09 · Contact Page — Hardcoded Address & Phone
**Severity:** Low  
**Description:** `contact-us.html` header shows "1442 Crosswind Drive Madisonville" and "+1 45887 77874" — these are template placeholders, not the real Al-Kahaf address.

**Fix:** Update with the real organization address and phone number.

---

#### BUG-10 · Free Trial Reminder Emails Partially Wired
**Severity:** Low  
**Description:** `trialEmailJob.js` cron job and `sendTrialReminderEmail()` exist, but it's unclear if the cron job is registered in `server.js` and running on startup.

**Fix:** Confirm the cron job is imported and initialized in server startup. Test with a trial account.

### 2.2 Known Responsiveness Issues

#### RESP-01 · Admin Dashboard — Welfare Cards Overflow on Mobile
**Description:** The welfare program inline mini-cards in the admin dashboard use a custom grid layout that collapses poorly on screens < 768px. Cards may overflow their container.  
**Fix:** Add `flex-wrap: wrap` and a min-width cap on card containers. Test at 375px.

#### RESP-02 · Welfare Program Add Page — Gallery Grid on Mobile
**Description:** The 3-column gallery upload grid becomes very small on mobile (< 480px). Each thumbnail cell is too small to tap comfortably.  
**Fix:** Switch to 2-column grid on `sm` and below. CSS: `@media (max-width: 575px) { .gallery-grid { grid-template-columns: repeat(2, 1fr); } }`

#### RESP-03 · Home Page — Project Cards Section
**Description:** The projects section filter tabs (6 buttons) overflow onto a second line on mobile, but lack proper wrapping styles. They can get cut off on screens < 400px.  
**Fix:** Add `flex-wrap: wrap; gap: 8px` to `.project-tabs` container for mobile.

#### RESP-04 · Welfare Program Detail — Donation Sidebar on Mobile
**Description:** On mobile, the donation sidebar is placed below the content. The sticky positioning becomes non-sticky on small screens, requiring scrolling back up to donate.  
**Fix:** Add a floating "Donate Now" button pinned to the bottom of the viewport on mobile that scrolls to the form.

#### RESP-05 · Admin Tables — Horizontal Overflow
**Description:** Admin list pages (students, enrollments, courses) use wide tables. On mobile these overflow horizontally without a visible scrollbar indicator. Users may not know to swipe.  
**Fix:** Add `overflow-x: auto` wrapper + a visual scroll hint (arrow icon or shadow on the right edge) for table containers on mobile.

#### RESP-06 · Navigation — Mobile Menu on iOS Safari
**Description:** The mobile hamburger menu may not close properly on iOS Safari when tapping outside the menu area, because iOS doesn't propagate click events to the `document` by default.  
**Fix:** Add `cursor: pointer` to the overlay div, or use a `touchstart` event listener alongside `click`.

#### RESP-07 · Home Page Hero — Text Overflow on Small Screens
**Description:** The hero section title ("Current Projects & Welfare Programs") can overflow or wrap awkwardly below 360px.  
**Fix:** Reduce `font-size` at xs breakpoint, or use `clamp()` for responsive typography.

## 5. Suggestions & Recommendations

### 5.1 Architecture

**Use environment-specific config files.**  
The frontend currently switches API base URL based on `window.location.hostname`. This is fine for simple cases, but as the project grows consider a proper build step (Webpack/Vite) that injects env variables at build time — prevents exposing dev/staging URLs in production builds.

**Migrate to a frontend framework gradually.**  
The vanilla JS approach works, but as pages grow to 94+ files, maintaining shared components (headers, footers, sidebars) becomes painful. Consider migrating new pages to Vue 3 (lightweight, progressive) or sticking with the current approach but extracting shared HTML via server-side includes.

**Centralize notification calling.**  
Currently `notifyAdmins()` and `notifyUser()` are called inline in controllers. Consider a `NotificationService` class that abstracts this and also handles the email fallback — keeps controllers clean.

---

### 5.2 Development Workflow

**Add a linter.**  
Add ESLint to the backend (Node.js) with the Airbnb or standard ruleset. This catches bugs like unused variables, missing `await`, and `console.log` statements automatically.

**Add API documentation.**  
With 102+ controller functions, new developers have no reference. Set up Swagger/OpenAPI using `swagger-jsdoc` — it auto-generates documentation from JSDoc comments on routes. Accessible at `/api/docs`.

**Write integration tests for critical paths.**  
At minimum, test: register → login → enroll → pay → certificate. Use `Jest` + `Supertest`. This prevents regressions when backend changes are made.

**Use a staging environment.**  
Before pushing changes to the live site, test on a staging URL (e.g., `staging.alkahafonlineacademy.com`). Use the same `.env` structure but a separate database.

---

### 5.3 Content & SEO

**Add meta tags to all public pages.**  
Course pages, blog posts, and welfare program pages should have unique `<title>`, `<meta description>`, and Open Graph tags (`og:title`, `og:image`, `og:description`) for better sharing on WhatsApp, Facebook, and search ranking.

**Add sitemap.xml and robots.txt.**  
A dynamically generated sitemap (listing all published courses, blogs, welfare programs) helps Google index the site. Block admin/student/instructor routes in `robots.txt`.

**Structured data (Schema.org).**  
Add `Course` schema for course pages and `NGO` / `DonateAction` schema for welfare program pages. This can unlock rich search results on Google.

**Image alt text.**  
Several images across the site have generic alt text like "Course image". Use descriptive alt text for accessibility and SEO.

---

### 5.4 Operations

**Set up error monitoring.**  
Integrate **Sentry** (free tier available) in both backend and frontend. It captures unhandled exceptions with stack traces in real time — you know about errors before users report them.

**Add health check endpoint.**  
`GET /api/v1/health` should return `{ status: "ok", db: "connected", uptime: X }`. Used by monitoring tools (UptimeRobot, etc.) to alert on downtime.

**Database backups.**  
Set up automated daily MySQL dumps to cloud storage (S3 or Google Drive). Retention: 30 days. This is critical for a platform handling donations and student records.

**Use a process manager.**  
Run the backend with **PM2** in production (`pm2 start src/server.js --name alkahaf-api`). It handles restarts on crash, clustering across CPU cores, and log rotation.

**CDN for static assets.**  
Serve CSS, JS, and image assets via a CDN (Cloudflare is free). This dramatically reduces page load time for users across Pakistan.

---

### 5.5 Welfare-Specific Suggestions

**Zakat / Sadaqah categorization for donations.**  
Let donors specify if their donation is Zakat (compulsory) or Sadaqah (voluntary). Generate a Zakat certificate for donors who need it for tax/religious purposes.

**Monthly donation / recurring giving.**  
Allow donors to set up a monthly automatic donation to a welfare program. This dramatically increases long-term fundraising consistency.

**Transparent fund disbursement reports.**  
Publish quarterly reports showing exactly how donations were spent per program. This builds donor trust and encourages repeat giving.

**Welfare program impact stories.**  
Add a "Stories" section to each program detail page — short testimonials with photos of real beneficiaries (with consent). This converts visitors to donors much better than statistics alone.
